# Module layout contract — version 14

Every module uses the host's `Screen` / `WidgetForm` presentation. The November 2, 2026 fullscreen and cache-list references define the shared proportions. Modules supply content and actions; they do not construct independent page layouts.

- Graph modules use two arrangements based on readable space. The graph stays above the list in small windows, including the initial 700 × 490 window and moderately enlarged floating windows. Side-by-side starts at a 944-point page viewport (approximately a 966-point outer window): 440 points for the list, 420 for the graph, the 24-point gap and shared side margins. Height alone cannot enable side-by-side. This applies only to a module's main page with a hero graph; drill-downs, Settings, Debloat and Siri & Apple Intelligence keep their existing list behavior.
- In the side-by-side arrangement, one ordered list occupies approximately 34% of available content, with a minimum of 440 points and maximum of 820 points. The graph takes the remaining width after the 24-point gap. Its top aligns with the actual top of the first list's background shade, below that list's header, using the measured header height and the existing header-to-shade spacing. This alignment follows header geometry rather than a fixed offset. The page uses its available width inside the shared side margins. Graph height responds to its width and available window height. The left list has its own vertical scroll view; the graph and its legend are fixed siblings on the right and remain in place while the list scrolls. The graph is rendered once and stays interactive. The graph initially aligns to the first list shade and retains that position after the list scrolls. Small/stacked views keep a single normal scroll view containing the graph, legend and list, so all of them scroll together. The shared page header and action dock remain fixed in both arrangements.
- During a wide module's initial scan, when no overview content is available, the loading graph spans the full content width inside the existing side margins. Its height is already the final right-pane graph height and stays unchanged through loading and the width transition. The same graph view remains mounted when data arrives. The host resizes it into its normal right-hand position with `ChartMotion.finishAnimation`, using the existing loading-finish spring, bounce and playback speed. At the spring's logical arrival, without waiting for residual bounce to settle, the existing `PageItemReveal` / `PageGroupShade` list cascade starts from its own first item. The separate list pane does not wait through the legend's stagger; compact pages keep their shared legend-then-list cascade. No new animation style or timing is introduced. Refreshes with existing list content keep the normal fixed-graph layout. Small/stacked views retain their current behavior. Interrupted loads invalidate obsolete reveal completions; Reduce Motion applies the final layout immediately.
- Page navigation uses the same `Theme.push` spring and slide/fade at every width. The host resolves the complete page in one geometry group before applying navigation, including module/settings swaps and folder/group pushes and Back. The list, graph and legend move as one page; fixed graph placement applies only to list scrolling. Child layout and value animations must not independently animate page placement. Loading's width resize and detail cascade remain tied to the loading state, rather than replaying because a page opens or becomes uncovered.
- Other adaptive pages use a centered canvas of approximately 80% of a wide window (up to 1,608 points), with 24-point gaps and at least 420 points per column. Half-screen and quarter-screen windows reclaim the side margins and reduce to two or one column. Row groups retain their ordering and stay together. There are no independent column scrollbars.
- `Screen.layout = .singleColumn` keeps settings-oriented modules in one centered list, up to 820 points wide. Debloat and Siri & Apple Intelligence use it. Settings and all its subpages use the exact same host width calculation and margins as these single-column modules (820 points maximum). Drill-downs use the same width. A missing layout field decodes as adaptive behavior.
- The host expands overview groups in place when they fit: up to 24 immediate rows in a readable column, eight below 420 points. Each group retains its title, count, total, item sizes, badges, Finder paths and actions. Longer inventories and deeper groups remain navigable, with their original complete data and identifiers.
- Selection groups remain on their dedicated page, including System Data app caches, whether or not their choices are saved. The front page shows the entry, count and total; opening it reveals the full list with section and row checkboxes, the selection action and its confirmation.
- Item and switch descriptions remain exclusively in the ⓘ information popover at every width. The host must never replace the icon with text underneath a row. Sizes, counts, state badges, actions and file locations remain on the row.
- Sections declare `SectionWidget.priority`: `.actionable` sorts ahead of `.normal` (or absent metadata), independently of the section's localized title or source position. Equal priorities retain source order. Free now uses `.actionable` in every storage module. The host keeps that section intact in the first list slot: top left beside the graph in an enlarged graph module, or first beneath the graph at the initial size. Other groups follow in stable order; selection groups inside Free now remain navigation rows.
- Graph annotations have a hard maximum of two lines total: one line for the name and one for its size. Long names truncate rather than gaining a third line. Outside-chart legend entries are indivisible single lines: marker, label and figure stay together. A measured flow layout wraps whole entries onto additional rows rather than wrapping their text or forcing equal-width columns. Only an entry wider than the entire graph may truncate its label; the figure remains visible and the complete text is available on hover. The chart, total and legend move together as one group during page navigation. Local value animations must not suppress the parent page transition; wide-page list scrolling still leaves the chart and legend fixed.
- Row action flags (Free, Delete, Uninstall, progress and outcomes) match public v1.1.5: with a size, the flag follows the title/information/Finder/badge cluster; without a size, it occupies the right edge.
- One main action remains pinned at the bottom. Confirmation, permission checks, refresh behavior, selection IDs, and cleanup semantics are unchanged by reflow. Resizing does not reset saved selections or replay the initial content cascade.
- Window corner behavior belongs to the host. Floating windows use the configured design radii. A macOS side tile, quarter tile or filled window uses the native window radius, resolved with AppKit's public concentric-corner API. A true full-screen Space uses the system's square outer boundary. Dashboard widgets use a 10-point radius while attached; grouped row surfaces use 10 points in every mode.
- Corner changes interpolate over 0.32 seconds in both directions. Window clipping, border, backdrop, zooming cards, tile fills, press overlays and shadow paths share the same state. State is per window and updates on moves, resizes, screen changes and full-screen transitions. Reduce Motion suppresses interpolation. Shadow paths and their transparent cutout follow the same interpolated radius and current frame as the glass; they must not start a separate radius animation. Resizes retire stale path animations, visibility fades only when the attached/floating state changes, and duplicate geometry notifications must not replay old corner states.

The SDK version is 13. It includes page-wide `Screen.selection`, stable `Selection.scope` and `ListWidget.fillsRemainingSpace` alongside lazy pages and native app icons. Additive optional segment kind metadata distinguishes folder destinations from file collections; optional segment selection supplies a file block’s batch action without adding a hidden selection to its overview. `Selection.partial` defaults to false when absent. The public Swift model layout changed, so all bundled module manifests use version 13; incompatible external modules are rejected before loading. Older saved screen JSON remains readable.

Verification covers layout boundaries, non-origin displays, every side and quarter with macOS tiling margins, false positives for floating edge windows, selection-page retention, semantic priority and stable ordering, Settings/single-list widths, row data preservation, legacy decoding, and rendered wide/half/quarter/single-column fixtures. Rendering fixtures do not execute cleanup or settings changes.

## Disk map and lazy module pages

The existing disk gauge remains the same rose, one-cell dashboard widget. It is now selectable and uses the same hover, press and zoom animations as other modules. Its destination is `com.macspace.disk-map`; the module must not add a second dashboard tile or change which other module is featured.

`MacSpaceModule.page(id:context:)` supplies a page on demand. `UsageSegment.pageID` makes a folder tile navigable; `Row.pageID` makes a navigation row without materializing a whole subtree. The host keeps these pages in the existing stack, with the same breadcrumbs, Back, slide animation, fixed graph beside an independently scrolling list at large widths, and the compact graph-above-list layout. Each page's own layout and cascade metadata apply. A row identity and its target page identifier may differ. Open pages reconcile after actions and refreshes; stale navigation or refresh completions cannot reopen a retired page. Old row/segment JSON decodes with nil navigation metadata. `Row.iconPath` draws the native application icon at the leading edge, using the existing row text, action, size and spacing rules.

The Disk root uses the review presentation specified below: Recommended, Apps, Folders, Large files. Apps and recommendations remain root-only; folder views use their own descendants. No broad category shell or age-based cleanup recommendation is presented.

Classification uses indexed names, extensions, bundle structure and locations, without reading file contents. Initial indexing and missing legacy metadata belong to one shared module loading operation with monotonic progress. No separate inventory loading page or Measuring badge is allowed. Ordinary loads do not rebuild unused category or age summaries.

Folder destinations must remain reachable. The shared graph presenter may aggregate small folder segments as Other folders, preserving every contained folder, its exact measured bytes and its original lazy destination. This changes presentation, never filesystem hierarchy or directory totals. Even a single tiny folder or a set of empty folders remains navigable. Other folders opens the standard grouped list; child rows retain their lazy `pageID`. Group navigation identities are scoped to the containing hero so nested aggregates never collide. The existing graph minimum-share affordance applies to an aggregate; individual tiny folders are not given invented sizes. Other files remains a distinct, lazy page of direct files below the large-file threshold. The folder-map legend and its cascade count use the same displayed grouping as the graph; the complete inventory is behind its normal navigation rows. Semantic smaller-item tiles in the other modules also retain their original file rows, actions, Finder paths and deeper destinations. A graph file group carries its eligible choices, permissions and scoped batch action in `UsageSegment.selection`, independently from the overview. Legacy segments may inherit their containing page’s selection. Aggregation combines only compatible actions and scopes; incompatible choosing groups keep their individual destinations. Its selection is normalized through the same host helper as a lazy file page; folder-only groups remain browse-only. Colliding legacy row identities keep their original subgroup pages instead of renaming action IDs or discarding items. The dashboard's existing block limit accounts for separate folder/file aggregates.

Recommended appears only when scoped candidates have actual modification-date evidence. Older documents/media, archives and known generated development outputs include files below 100 MB; the large-file threshold belongs exclusively to the Large files filter. Pure size filters and unmatched app data are not duplicated as recommendations. Cached source-category membership and totals establish whether a recency query covers its entire corresponding content category; such a query is omitted rather than advertising the same inventory under another title. Recommendations are explicit review subsets with a stable reason in the ordinary information control, not claims of junk or safe automatic cleanup. Missing and future timestamps do not qualify. File rows show Not modified since, never Unused. Modification recency, app ownership and actual usage remain separate. No file-open surveillance, speculative duplicate detection or usage claim is introduced.

The startup map includes the sealed system and Data volumes through their ordinary root paths. External mounts, virtual devices, duplicate `/System/Volumes` views and the index's own cache are excluded. Allocated local bytes include small files; file metadata is persisted on disk while Swift projections retain only the current bounded pages and large-file overview data. Symlinks are not traversed, hard links count once, and cloud-only content is never downloaded. APFS clones/snapshots and unreadable locations can differ from volume usage; the map identifies the remaining protected/other usage and explains the estimate in its information popover.

The index and an FSEvents watermark persist across launches. File events trigger shallow reads of affected parent directories; new folders and explicit subtree invalidations recurse only through those branches. Parent totals reconcile from cached children. Dropped/coalesced events remeasure the affected subtree; an explicit Refresh may request a complete scan. Concurrent tile/page requests share a scan. App actions immediately invalidate their affected paths rather than waiting for file events or rescanning the disk.

File category pages use exactly the app-cache choosing behavior: unchecked eligible rows, a shared yellow Free selected button with allocated-byte totals, permission checking, confirmation and one batch action for exact selected IDs. Individual files show their name, size and Finder control without an information pill or per-file Delete action. Subtitles remain reserved for quantity sums and counts; paths stay in Finder controls. Different folder/filter inventories do not carry hidden choices into each other. Pagination of one inventory preserves only explicitly selected off-page IDs and sizes. Returning to a visible row that loses eligibility excludes its old choice. Successful removals discard selected metadata even when a synchronous action finishes before queued progress updates. Leaving a graph group, inventory or module clears its ephemeral choices. The overview’s visible Large files preview shares its scoped selection with More items; unrelated type filters have independent scopes. Execution resolves all IDs against the current index and folder boundary before mutation, revalidates regular-file ownership and canonical paths, and reports partial failures. Protected files remain visible without an enabled checkbox. No operation runs automatically.

Uninstall discovery separates installed user apps from protected system components, background components, additional copies and MacSpace's own lifecycle. The main app list counts installed user apps only; system components and other copies have a separate page. App icons use the native app bundle icon. Menu-bar UI apps use the same eligibility as other installed apps; true background-only components stay separate. Registered build/download copies remain separate when an installed Applications copy of the same identity exists. Eligibility reasons remain in the information control; ownership categories are reviewable on each app's data page. Apple bundle identifiers alone do not establish filesystem protection.

The catalog and ownership rules are app agnostic: bundle and signing identities, container metadata, signed app-group entitlements, declared helper requirements, and bounded read-only receipts provide evidence. Display names, identifier conventions and vendor-specific metadata never authorize automatic deletion. Filesystem UID identifies the account independently of app ownership. Measurement persists UID and app evidence; file pages resolve the same ancestor claims. Claims distinguish verified-exclusive, shared, inferred and unknown ownership. System and embedded bundle identities collected by the scanner also participate in matching, including extension bundles outside `.app` directories. Installed components must not be advertised as missing apps based on the limited uninstall catalog. The index’s Data-volume paths and live filesystem paths normalize consistently for evidence lookup.

Unmatched app data is an honest review page, not proof of removed apps or a safe-cleanup recommendation. It excludes zero-allocation entries, measured installed identifiers, matching container identities and paths claimed by installed apps. It uses a single flat list with one row per location, a factual location-kind badge and Finder control; it never wraps one item in a same-named group. Only eligible canonical user-owned immediate child folders of the recognized user Library data locations can be explicitly selected. Shared app-group locations and installed-app claims remain excluded. The existing yellow Free selected button presents an explicit permanent-removal confirmation explaining that the data may contain documents and settings. A destructive request refreshes the catalog, resolves every opaque choice to the exact reviewed path and filesystem identity, rejects stale or forged selections before any mutation, revalidates each target immediately before removal, and never expands the target set. This manual decision does not change uninstall’s verified-exclusive ownership rules.

The preview serializes an exact removal plan, including installation identity, target identities and ownership evidence. The module and helper use the same catalog rules and reviewed discovery candidates. The helper independently rereads identities and eligibility, rejects missing/stale/forged/overlapping targets before side effects, and executes only reviewed targets, data first and bundle last. It never adds targets during execution. Uninstall uses the existing confirmation, Full Disk Access and helper flow; MacSpace removal uses its dedicated Settings lifecycle. A bounded public app catalog cannot prove complete exclusive ownership: conventional support paths, uncertain containers/groups and historical receipt data stay out of automatic removal. Privileged-helper lifecycle removal remains unsupported and is preserved for review. There are no app-specific cleanup rules.

Navigation reads the latest completed disk snapshot immediately, without draining events, reconciling the disk or saving a cache. Reconciliation runs separately for changed branches; destructive requests await a current snapshot. A map snapshot retains only its direct large files; it never loads all descendant large files on each folder navigation. Descendant file inventories use bounded lazy queries. Catalog and ownership metadata refresh on catalog changes or its bounded refresh interval, not every file-byte revision; existing app pages use the completed catalog. Initial app discovery and evidence attribution run in the background; the disk map and cached pages never await them. An app page opened before the catalog arrives shows the shared reading message and refreshes normally. Full code-signature validation runs for the selected app before uninstall, rather than for every app while browsing. Signing identity metadata is still recorded in the catalog. Database writes remain off the navigation path, with one serial writer and a separate completed reader. The host keeps at most 12 inactive/active lazy pages unless the open ancestry itself is longer, reopens cached pages immediately, invalidates closed pages when data changes, and refreshes only the visible page during polling (all ancestors after mutations). Chart pointer movement reuses one geometry arrangement, and legend color ramps are computed linearly without changing appearance or animation.

The disk scanner streams native `getattrlistbulk` entries through a fixed 256 KB buffer; it must not retain Foundation URL arrays or autoreleased metadata across the whole walk. Modification timestamps are requested only by Disk's measurement, in the same native entry buffer. A newly discovered cloud-only directory is recorded without searching the existing index, and removing a cached branch visits only that branch's child links. Application inventory consumes the embedded identities already collected by the disk scan rather than walking every app bundle again. The complete directory/file index and ownership evidence stay in SQLite with bounded page caches, no memory mapping, disk-backed temporary work and prepared parameterized queries. Swift snapshots retain only page projections and direct large-file data; small-file/category queries return at most 200 file records. Hardlinks contribute bytes once. If a hardlink identity cannot be read, it must never trigger a metadata update for the empty unlinked identity; the affected directory is marked incomplete. Incremental rereads replace metadata only for changed parents. The retired framed cache is no longer read or written; existing SQLite indexes missing small-file/category/recency metadata collect it once inside the module loading operation, in an unpublished generation. A full generation is published through an atomic pointer only after completion. A whole-disk Swift/JSON object graph is forbidden. File lists, category browsing and recommendation navigation do not rescan the filesystem. A fresh whole-disk read is distinct from a cached reopening; performance checks never perform cleanup.

Directory byte totals reconcile from cached children in child-before-parent order. Content-type filters use bounded indexed inventories. Ordinary scans do not renew age summaries. Legacy metadata migration is separate from normal reopening and never classifies a file as unused. Request identifiers and selection scopes are deterministic and folder/filter-specific.

Narrow folder queries use indexed path ranges; Large files uses its partial size index. File inventories are ordered by parent folder, then descending size and path, with bounded cursor pages.

Hard-link identity reads and updates must use their nonempty-identity partial indexes. Performance coverage must include native hard-linked files against a large unrelated inventory, verify allocation is counted once, and verify size changes propagate to aliases outside the changed folder. Synthetic insertion benchmarks alone do not establish whole-disk startup performance.

Initial Disk inventory collection uses at most eight shared native workers, fixed buffers and 256 buffered file records per worker. Database writes are serialized in batches. An unpublished fresh index builds lookup indexes once after collection. Collection, index construction and byte-total reconciliation report through the same loading relay.

Hard-linked names must not cause repeated rewrites of an unchanged inode family. Fresh collection records each name once; incremental reconciliation compares an indexed representative and updates aliases only when their metadata changed. Performance coverage includes thousands of aliases for one inode, concurrent per-folder accounting, and an opt-in complete backend scan plus cached reopening. The opt-in diagnostic writes only a separate temporary index and never launches the app. Initial scanning and cached reopening are reported separately; synthetic timings must not be presented as whole-disk results.

## Disk review presentation and removal settings

The Disk overview presents Recommended (content-verified duplicate review and the existing System Data developer-cleanup destination), Apps (uninstall and unmatched app data), nonempty personal Folders (Downloads, Documents, Desktop), then a bounded Large files preview with More items at 100 MB. Broad content categories and age-only recommendations are absent from the overview. File inventories group their rows by folder, provide Finder access, and use quantity/count subtitles only. Large files offers Archives / Installers / Media / Other as subfilters. Folder totals include all measured allocation; file review remains explicit, unchecked and scoped. Protected/app-managed files remain visible for Finder review without deletion choices.

Settings › General has “Move files to Trash”, off by default. Ordinary selected Disk files are permanently deleted by default; enabling the setting uses Trash. Confirmation text and execution must agree; changing the setting invalidates an already prepared removal confirmation. App uninstall and cache cleanup retain their own explicit lifecycle rules. Read access cannot be inferred from modification dates; no item is labeled unused from age alone.

Duplicate comparison is an explicit action using the existing progress button, not an extra phase of module loading. It streams local eligible personal files of 100 MB or more with matching sizes, verifies complete contents, excludes hard-linked aliases and preserves at least one copy. Results are paginated; the selected copy and a remaining copy are verified again before removal. Nothing is preselected. File-list headers support selecting the eligible rows in their list, including single-column pages.

Disk cache retention keeps the active generation and its sidecars, removes abandoned UUID generations at boot and deletes retired generations after the reader switches. Legacy framed cache files are retired. Finder review, module navigation and menu-bar navigation must use the same destination/tint. Returning to a loading tile uses the existing chart closing/opening animation.

Developer cleanup may offer Rust target and Swift .build folders only with a parent manifest and tool-generated metadata, never source project roots. These are manual review items and retain running-process/open-file safeguards. System Data cleanup schedules at most two disjoint cache entries together; overlapping paths and Homebrew remain serial, with fresh checks per entry.

The November 3 completion review supersedes the earlier category-summary implementation notes: ordinary Disk scans maintain directory allocation totals and bounded file inventories, but no longer rebuild content-category or age-review summaries. Two redundant global file indexes and old summary rows are removed in a one-time compacted generation. The active database is preserved until migration completes; its size is measured, not claimed to have a universal cap.

Current open-file evidence is the approved scope. File pages identify observable processes holding a descriptor, using canonical paths, and exclude these files from selection. Execution checks open descriptors again and rejects ownership claims in its backend target lookup. Absence of an observable descriptor never means unused or safe. Historical reads and a system extension are outside the approved scope. Filters have separate selection scopes. Inventories paginate in parent-folder order so groups do not interleave across pages. Finder controls for folders open their contents directly.

Developer cleanup opens a dedicated System Data page through a retained page request, and its measured total comes from the same developer/Homebrew entries. If no recent measurement exists, no size is fabricated. A selectable single-list screen without a title uses the page title and receives the existing select-all section behavior.

## Implemented Disk contract — session selection and compact inventory

Disk overview has Apps, Folders and Large files and duplicates. Duplicate files is the first destination of the last class; nonempty Archives, Installers, Media and Other follow. No Recommended or developer-cleanup row is exposed by Disk. Recognized Applications maps add app management and unmatched-data review at their top. Managed personal-root exclusions are shared by inventory and ordinary removal; caches, package internals and System Data/developer targets are not ordinary Disk candidates.

Category pages use one grouped-list surface containing lightweight folder headings with Finder and scoped selection. Category and folder headers resolve the full eligible current-size inventory across pagination. Show smaller files replaces the current category page in place, rather than extending the breadcrumb stack, and never automatically selects revealed files. Finder/navigation and keeper rows have no disabled checkboxes. Other folders opens the actual contained folder forest as a map, including nested/empty aggregates; Other files remains a file inventory. Standard top-right Refresh supports the visible scope. Routine root refresh reconciles events plus root children, not a forced full disk rebuild.

Explicit Disk selections survive categories, folders, Back, pagination and leaving/returning during the app session. A frozen disk-backed version retains original file identity and duplicate provenance; the host holds count/bytes and bounded visible membership. No 10,000-file selection ceiling exists. Full mutation preflight runs in bounded pages before removal; one post-action delta snapshot removes only completed choices. Unknown/expired/changed inventory fails closed. Duplicate keepers cannot appear in the complete selection, and their original identities are checked again before each copy removal. No separate review page is implemented.

SQLite stores each measured folder path once with integer parent IDs. Eligible large files and necessary hardlink allocation records use parent IDs and leaf names; ordinary small-file details are not persisted globally. Smaller-file browsing uses a bounded temporary window, while full category selection streams independently of that window. Bottom-up ordering indexes use integer IDs rather than another full-path copy. Missing/incomplete initial commits are discarded on retry. Completed cached projections publish before background branch reconciliation. Snapshot requests used by mutations await current reconciliation and filesystem-event replay.

Duplicate work is automatic, cancellable and outside the serial writer: metadata candidates, distinct inode staging before content reads, cached samples and full digests, verified-set publication. One reusable 256 KiB POSIX buffer serves reads; fixed batches carry metadata. Fingerprints invalidate on device/inode/UID/size/mtime/ctime changes. Incomplete reads report unknown, never unused. No Compare button exists.

Ordinary removal is explicitly unprivileged (real/effective UID must agree and be nonroot). Approved personal roots, flags, ownership, no-follow ancestors and original identities are enforced at execution. Confirmed permanent/Trash mode is frozen across the action. Permanent removal uses a guarded rename and descriptor unlink; Trash uses the original URL under coordination so Finder preserves filename/Put Back. Coordination does not establish atomicity against uncooperative same-user processes. Unmatched-data recursive removal is a separate permanent lifecycle with bounded batch/descendant preflight, private on-disk manifest, no-follow descriptors and recovery of unremoved data on failure. No uncertain descendant is deleted just because its top folder was selectable.

System Data cleanup returns typed target outcomes rather than parsing result text. Only affected measurements reconcile; stale scans cannot overwrite post-mutation publication. App/container caches, developer outputs and Homebrew retain fresh running/open-file checks. Unknown volume reclamation is not subtracted from individual rows. The snapshot, graph and widget update from one verified result; global free-space settling is not an unrelated presentation barrier.

Shared contract is SDK 13; all bundled manifests agree and older binary layouts are rejected. Optional additions retain defaults for old saved JSON. User performs app/visual verification; automated checks must exclude rendering/screenshot tests.
