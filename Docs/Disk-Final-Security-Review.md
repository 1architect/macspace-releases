## Implemented storage design and release requirements

### Authenticated metadata encryption

The source implementation uses SQLCipher for inventory/selection databases and authenticated binary receipt payloads (the legacy `.receipts.json` filename remains recognized). Before migration, existing deployed inventory and receipt JSON may still expose:  paths/names, sizes, timestamps, ownership associations and duplicate fingerprints are sensitive derived data. File permissions/private directories do not provide same-user confidentiality. A passing SQLite structural check does not authenticate user intent or establish confidentiality. Anonymous frozen-selection and guarded-removal manifests remain authenticated with fresh process-held keys. Release acceptance is separate from these source changes.

### Mandatory no-popup requirement

**The user's requirement is no Keychain popup EVER, in any situation.** MacSpace must never request or trigger a Keychain unlock, password, permission/Allow/Always Allow, biometric or other authentication dialog for its metadata encryption. This covers first launch, ordinary reads/writes, key creation, migration, rotation, deletion, update, reinstall, error recovery, foreground UI, background work, CLI and any helper path that needs a key.

If silent access is unavailable, the operation must stop or skip the encrypted cache without requesting interaction. It must not retry interactively, ask the user to unlock the Keychain, open Keychain Access, relax access controls, persist a key elsewhere, or fall back to plaintext. A normal nonmodal unavailable status is acceptable; a Keychain authentication/permission popup is not. Disallow an implementation path if its noninteractive behavior cannot be established.

The proposed implementation should use an explicitly noninteractive authentication context (`LAContext.interactionNotAllowed = true` supplied with `kSecUseAuthenticationContext`) for relevant Keychain operations. Do not rely on an omitted/default authentication policy: Apple's default permits UI. The older `kSecUseAuthenticationUIFail` is a compatibility API, not the preferred modern design. Treat interaction-required, locked/unavailable, access-denied and entitlement errors as failures with no interactive fallback. [Apple authentication UI policy](https://developer.apple.com/documentation/security/ksecuseauthenticationui), [Apple noninteractive context](https://developer.apple.com/documentation/localauthentication/lacontext/interactionnotallowed), [Apple compatibility API](https://developer.apple.com/documentation/security/ksecuseauthenticationuifail).

Use no user-presence, password, Touch ID or biometric access-control requirement and do not call authentication or unlock APIs to obtain the key. Prefer a suitable macOS Data Protection Keychain design over legacy file-Keychain ACL prompts, subject to verifying the actual signed distribution's capabilities and entitlements. An access-group setting alone does not prove this no-popup requirement. [Apple Data Protection Keychain](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain).

This records a release acceptance condition, not a claim that an unimplemented design has already guaranteed every OS behavior. Code-only tests cannot prove the absence of OS dialogs across signing and account states. The user handles app/UI verification; do not launch the app or exercise UI to test this without an explicit request.

### Encryption and key ownership

- Use an established authenticated database-encryption implementation, with SQLCipher as the candidate for evaluation. Cover every inventory/generation database, sensitive persisted selection/editing state, receipt cache and sensitive journal payload. Define and inspect the actual WAL, rollback, shared-memory and temporary-file behavior; encrypting one main file is insufficient. SQLCipher documents encrypted journal/WAL pages and requires special care for temporary storage. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/).
- Generate unpredictable random key material. Persist it only in correctly restricted Keychain items accessible to the explicitly authorized signed MacSpace components that need it. Verify distribution entitlements and app identity on real release builds. Do not grant every app signed by the developer access. Do not put keys in the app bundle, preferences, source, command arguments, logs, environment variables or the cache directory.
- Choose accessibility and synchronization policy deliberately for background use, without authentication requirements. Do not silently broaden access to make background work succeed. If the chosen policy makes a key unavailable while locked or before login, skip/defer that work silently.
- Authenticate the data and bind trusted operation records to their account, schema, purpose, selection/operation identity and expected version. Database page integrity alone does not establish fresh user consent or protect against every replay of an older valid database. Retain independent live filesystem, permission, ownership and helper authorization checks.
- On migration, close readers/writers, retire frozen tokens, safely remove recognized disposable plaintext caches and sidecars, and rebuild only into encrypted storage. Never trust a legacy plaintext selection as authority for deletion. Do not claim that unlinking plaintext guarantees physical erasure from APFS snapshots, backups or SSD storage.
- If a key is missing, do not replace it while treating existing ciphertext as valid or overwrite recovery journals. Disposable inventory may be safely discarded and rebuilt only after a new restricted key can be created silently. Preserve non-disposable rollback/recovery records and report unavailable recovery without prompting or executing unauthenticated content.
- Keep descriptor/no-follow and owner/link checks, permissions, retention limits, cache cleanup on uninstall and sensitive-data minimization. Encryption does not repair pathname races or turn cached data into authorization.

### Trust boundary and Full Disk Access

The goal is to protect cached metadata against ordinary unrelated applications that can otherwise copy same-account cache files. Full Disk Access authorizes MacSpace to read protected data; it is not root and does not make retained metadata harmless. A malicious separate process should not inherit that access through cache or selection tampering.

Code running inside a compromised MacSpace process can use its available keys and Full Disk Access. Encryption cannot prevent that. Keep signed-code integrity checks fail-closed, Hardened Runtime and library validation intact, and avoid debugging/unsigned-library exceptions in distribution builds. Restrict helper operations independently. A compromised operating system remains outside this encryption boundary.

### Required evidence before calling encryption complete

1. Automated key-store tests cover every lifecycle operation, including failures, and assert that noninteractive policy is always supplied and no fallback path requests authentication or writes plaintext.
2. Inspect disposable database, generation, receipt, journal, WAL and temp artifacts for sensitive plaintext. Test wrong/missing keys, tampering, old valid database replay and legacy migration without deleting real user data.
3. Verify signed release identity/access groups across first launch, ordinary update and signing-certificate rollover, reinstall, changed/missing entitlements, locked/unavailable Keychain, missing/replaced key, account/password/Keychain reset, background execution and uninstall. None may produce a Keychain popup; failures must remain noninteractive. UI portions require the user's explicit request and verification.
4. Measure scan, pagination, duplication, memory and background performance with encryption enabled. Verify failed key access cannot accidentally publish actionable stale selections or prevent unrelated cleanup from finishing.

The source now encrypts inventory and receipts and implements the noninteractive key policy. Until signed-distribution evidence exists, describe zero-popup behavior as an implementation awaiting release acceptance; do not claim verified OS behavior or imply that the existing installed app/cache was migrated.

## Implemented cleanup behavior

Cleanup rows publish a `CleanupTarget` in `Row.cleanup` instead of a per-row Free action. The target has a stable operation ID, the current allocation estimate, the guarded module action, availability and an automatic-execution policy. Utility actions remain ordinary row actions. Shipped cleanup modules do not publish tile Free shortcuts or aggregate Free primaries that could bypass selection.

The host draws the same left checkbox for rows and drill-down headings, and one Free selected action for the active cleanup scope. Confirmations and permissions are assembled from the selected targets. A batch validates its selection and permissions before mutation, executes existing module handlers sequentially and reports partial failures and completed allocations. An already-running cloud job remains a progress row, without a second Free button or a premature completion celebration.

The host stores explicit true and false preferences per module, preference scope and stable ID for renewable choices that remember selection. Preference keys are encoded tuples, not localized titles or measured sizes. Temporarily absent rows retain their decisions. Newly discovered optional operations start unchecked. Existing recommended cache, report and purge defaults apply until explicitly changed. A completed renewable cleanup does not clear the future preference.

App-cache sub-selections retain the module's `CacheChoices` contract. The host also writes each checkbox and section decision synchronously; System Data applies those decisions to snapshots and automatic execution even before the compatibility save action finishes. Selecting all of a cache section retains its established meaning for later entries in that section. Backup-disk selections are per-visit choices by destination ID and backup stamp, start empty, and always retain their manual review flow. Older saved backup preferences are ignored.

### Nonrecoverable cleanup

The public release baseline is [v1.1.5](https://github.com/1architect/macspace-releases/releases/tag/v1.1.5), confirmed as the latest non-prerelease on 2026-11-06. Its scheduled System Data cleanup includes selected caches, old diagnostic reports and unused assets; Other System Files purges app-marked purgeable files. It does not schedule Trash, unified-log erasure, document version-history deletion or local Time Machine snapshot deletion. Old reports retain that existing policy; this change does not reclassify every historical record as a new destructive category.

Both module settings contain **Clean non recoverable items automatically**, option ID `cleanNonRecoverableAutomatically`, default **off**, stored independently per module. System Data applies it to Trash, unified log and version history. Other System Files applies it to local snapshots only. Per the user's explicit decision, backups on connected backup disks remain manual even when the toggle is on; the newest backup stays protected.

| Setting | Manual module visit | Scheduled cleanup |
| --- | --- | --- |
| Off | The nonrecoverable items start unchecked; the user selects them for that cleanup. Completed choices clear, and leaving the module discards any remaining temporary choices. | Those operations are excluded even if an old saved checkbox is true. |
| On | Currently available nonrecoverable items start checked on each visit. The user may uncheck them for that visit without changing the settings toggle. | Currently available nonrecoverable operations are included through the existing guarded handlers. |

These targets publish `remembersSelection: false`. Their checkbox overrides live only in the host's current module visit; old true/false preferences never override the setting. With the toggle on, a manual deselection does not opt out of scheduled cleanup: turning the settings toggle off does. A changed default invalidates the old visit override. Ordinary renewable choices continue to persist. Manual confirmations and permissions remain; the toggle does not enable the global scheduler, bypass eligibility/backup-in-progress checks or allow deleting the latest protected snapshots/backups.

Screen loads, live status updates, post-action presentations and fresh automatic-cleanup screens all receive the current option. The module handlers also reject automatic destructive requests without opt-in before scanning/mutating; backup-disk requests reject automatic execution regardless of the toggle.

Automatic cleanup receives the preferences through `ModuleContext.cleanupChoices` and resolves a fresh module screen's currently available automatic targets. It uses the same guarded handlers as the UI. Unchecked, unavailable and manual-only targets are excluded. Missing permissions are skipped with details; app-cache jobs pass the automatic flag and leave running applications alone. Retention, ownership, open-file, cloud upload, model-use and backup protections remain in the existing engines. Choices changed during a running cleanup apply to subsequent runs; the already-started work keeps its existing lifecycle.

Ordinary file deletion and app uninstall selections remain session choices and retain their manual review. Background feature lifecycle tasks (for example releasing a model after its feature was explicitly disabled) remain separate from the scheduled cleaner.

All bundled manifests now use SDK 22 for structured selection parameters; SDK 21 introduced `CleanupTarget`'s selection-persistence layout. Older contracts are rejected by the normal module compatibility check. Older JSON without the new policy decodes with its previous persistent behavior; the freshly built module policy decides which operations require new consent.

## Finding details from the audit snapshot

### SEC-009 — Medium safety risk: legacy System Data deletion does not pin its filesystem boundary

- Locations: `Modules/SystemData/Module/SystemDataModule.swift:371–391` (Trash), `Modules/SystemData/Module/Engine/SystemDataInspector.swift:1017–1067` (cache cleaner), `Modules/SystemData/Module/Engine/DiagnosticReportCleaner.swift:78–90` (reports).
- Evidence: Trash enumerates its supplied/default root and recursively removes its named children without a no-follow root descriptor. Cache cleanup checks resolved paths and current ownership, but later renames and recursively removes by pathname without a verified post-rename identity. Diagnostic execution checks only current regular-file type and age, not the original device/inode or pinned ancestors.
- Reachability: `SystemDataModule.handle` invokes `emptyTrash`, `cleanReports` and ordinary cleanup; `cleanSafe` also reaches report/cache cleanup, while developer cleanup delegates to `SystemDataCleaner`. These are separate from the newly guarded DiskMap app-removal primitive.
- Preconditions and potential impact: a local process must be able to replace a cleanup root/ancestor or selected entry during an authorized cleanup. A substituted root or old regular file is not necessarily the object the user intended to free. Operations run with the app user's permissions and potentially its Full Disk Access. No root escalation or TCC bypass is established.
- Confidence: source-confirmed missing boundary/identity checks; no replacement/deletion demonstration or live Trash cleanup was performed. The report cleaner is unchanged from main. The branch strengthens some ordinary cache checks, but still leaves the pathname gap; Trash's path-based removal also predates these retained fixes.
- Remediation: pin the actual Trash/report/cache roots with no-follow descriptors, freeze target identities, and use guarded descriptor-relative operations. Preserve any unexpected or replaced entry. Regression coverage should include root links, changed ancestors/entries and changes during cleanup without touching real user data.
- Status: implemented in the current source; see the remediation status and validation record above.

### SEC-010 — Low availability risk: external cleanup runner has unbounded output and post-timeout waits

- Location: `Modules/SystemData/Module/Engine/HomebrewCleanup.swift:112–135`; callers include `HomebrewCleanup.plan`, `DeveloperCaches.unavailableSimulators/free` and `SystemDataStore.liveSnapshot`.
- Evidence: both pipe readers accumulate `readDataToEndOfFile()` into memory. After the configured wait, the runner sends termination, waits at most another five seconds for the parent, then calls `reading.wait()` without a deadline. A child that stays alive or a descendant retaining an output pipe can prevent EOF indefinitely. `process.terminationStatus` is then used without establishing that the child actually exited.
- Impact and limits: a stuck external tool can stall System Data reading or cleanup and its serialized lifecycle/uninstall work; unusually large output is also uncapped. No external process was deliberately hung or used to demonstrate memory exhaustion. This is an availability/robustness finding, not evidence of remote command injection.
- Remediation: bound collected output, apply a shared deadline to process exit and pipe draining, safely terminate owned descendants where supported, and return an explicit timeout instead of waiting indefinitely. Test with an injected process/stream abstraction.
- Status: replaced by the bounded runner in the current source. No code was changed for this finding.

### SEC-011 — Medium integrity risk: owner rollback provenance is not authenticated

- Locations: `Platform/AssetOwners/AssetOwners.swift:194–218,783–840`; journal location in `Platform/AssetOwners/AssetModelCleanup.swift:69–71`.
- Evidence: the journal checks file type, UID, permissions, stored version/scope/UID, and secure decoding classes. Those checks do not authenticate which entries MacSpace actually saved. Restore then takes client/name and archived subscription/assertion content from those entries. Per-scope release allowlists are not reapplied to every restored entry; an existing live request is compared with that same saved content, while an absent request can cause a subscription/assertion submission before the resulting state is checked.
- Reachability: `restoreOwners` requests this path on supported builds; Siri uninstall preparation explicitly iterates saved scopes and requests owner restoration.
- Preconditions and potential impact: another process must be able to modify the same account's owner journal while preserving its checked owner/mode and supply decodable content. The app can then treat modified records as prior user intent, potentially altering restored owner state or blocking restoration/uninstall. This is a provenance/integrity gap, not a demonstrated privilege escalation or new ability to call the underlying OS services.
- Confidence and limits: source-confirmed missing journal authentication and incomplete scope binding. No journal was modified and no owner API was invoked to validate downstream OS acceptance. Existing secure decoding and current-state comparisons remain meaningful protections; they do not establish record provenance.
- Remediation: authenticate journal contents and bind scope, account, operation identity, client/name and archived content to protected provenance. Independently validate restored record shapes and scope membership before a native mutation; reject legacy/unverifiable journals without replaying them automatically.
- Status: the current implementation covers authenticated rollback and temporary-owner recovery separately; live native verification remains pending.

### SEC-012 — High potential impact: cached dashboard actions are usable before a fresh module read

- Locations: `App/Settings/SettingsStore.swift:39–47`, `Sdk/Interface/Tile.swift:36–41,65–67`, `App/Registry/ModuleHandle.swift:770–772,788–802,1079–1148`, `App/Shell/HomeView.swift:28–39,827–842`, `App/Shell/TileArt.swift:931–988`.
- Evidence: UserDefaults stores/loads the complete Codable tile, including its `switchAction`. `TileInfo` copies that action even when `tileIsStale` is true. Dashboard `TileSwitch` disables only when the action is nil, forwards the retained action to `handle.perform(..., quiet: true)`, and does not ask for its confirmation. `StateView`'s loading flag does not disable its switch. The handle becomes ready before its first awaited refresh completes; ordinary non-cleanup-batch dispatch does not rebind the supplied action to a current live tile or check `tileIsStale`.
- Preconditions: another process must be able to alter the same account's cached tile preferences, the affected signed module must load, and the user must interact with the cached dashboard switch before fresh metadata replaces it. This is not a remote or interaction-free issue.
- Potential impact: display cache data can become action authority. Some module handlers perform irreversible or privileged operations using the app's already-approved authority, while the cached action carries its own parameters/permission metadata and enters a switch path without destructive confirmation. Individual module and helper guards still apply; this finding does not establish that every forged action would succeed or bypass root-helper caller validation.
- Confidence and limits: source-confirmed trust/dispatch gap. No preference was modified, no app/UI interaction occurred, no forged-action fixture was run and no system action was executed. End-to-end interaction timing and downstream OS authorization remain unverified, so the High rating describes potential impact rather than a demonstrated root exploit. The cached-switch path also exists on main; these retained fixes do not change it.
- Remediation: persist display-only tile summaries, obtain actionable definitions only from fresh trusted module output, disable cached controls until that output is ready, and validate the requested operation/parameters/permissions/confirmation against the live action contract at dispatch. Test stale/corrupt display caches using inert injected module callbacks.
- Status: implemented in the current source; see the remediation status and validation record above.

### SEC-013 — Medium selection integrity risk: newline-delimited opaque IDs do not round-trip safely

- Locations: `Sdk/Interface/Widgets.swift:789–792` (`Selection.parameter/ids`), `Modules/SystemData/Module/Engine/SystemDataInspector.swift:895` (cache IDs derived from entry names), `Modules/SystemData/Module/SystemDataModule.swift:99–102`, `Modules/SystemData/Module/Presentation/SystemDataCleanupChoices.swift:21`.
- Evidence: the SDK joins opaque IDs with a newline and splits incoming parameters on every newline. Cache IDs include filesystem entry names, which are not restricted to exclude that character. System Data takes the parsed IDs and filters current cache entries by membership, without requiring an exact round-trip to the original selected IDs. The typed top-level cleanup batch does not repair the nested cache-ID serialization.
- Preconditions and potential impact: a local process must control a discoverable entry name, and the user must select the resulting row. A single opaque selection can be interpreted as multiple IDs, potentially selecting a different existing cache/developer cleanup entry. Live availability, ownership, running-process and cleanable-location checks still apply; this is not arbitrary-path or root deletion.
- Confidence and limits: source-confirmed ambiguous encoding and receiving subset filter. No special entry name was created and no substituted selection or deletion was executed. Ordinary Disk file IDs use Base64 paths and do not have this specific raw-name ambiguity.
- Remediation: use an unambiguous structured encoding for opaque ID arrays, enforce bounds and exact identity-set validation at consumers, and reject ambiguous legacy parameters rather than silently accepting a matching subset. Cover newlines, commas and Unicode in inert selection round-trip tests.
- Status: implemented in the current source; see the remediation status and validation record above.
